# ทำอะไรไปบ้าง และควรอธิบายอาจารย์อย่างไร

## 1. เริ่มจากปัญหา ไม่ใช่เริ่มจากเลือกโมเดล

ผมเลือกทำผู้ช่วยยืมอุปกรณ์ เพราะคำถามจริงมีสองลักษณะ: กฎที่เป็นข้อความ กับจำนวนของที่เป็นตาราง เช่น “กล้องว่างกี่ตัว และเงินประกันเท่าไร” ต้องใช้สองแหล่ง ไม่ควรให้ model เดาสถานะจากความจำ

## 2. สร้างข้อมูลของเราเอง

สร้าง policy 18 หัวข้อและอุปกรณ์ 12 ชิ้น ทุกอย่างสมมติและเขียนชัดว่าไม่ใช่ข้อมูลมหาวิทยาลัยจริง ช่วยให้ commit raw data และทดสอบซ้ำได้ แต่ยังไม่ใช่ validation กับผู้ใช้จริง

## 3. ทำ tool ที่ควบคุมได้

`search_docs` ค้นคู่มือ ส่วน `query_inventory` รับ category/code/status แล้วโค้ดสร้าง SELECT ที่ใช้ parameters ไม่ให้ model ส่ง SQL อิสระ เปิดฐานข้อมูลเป็น query-only และไม่มี tool จองหรือชำระเงิน

## 4. ต่อ agent loop

ส่งคำถาม + tool schema ให้ model → model ขอ tool → โค้ด validate และรัน → ส่งผลเป็น role tool ที่มี tool_call_id → เรียก model อีกครั้ง หยุดเมื่อไม่มี tool call มี max_steps=5 และ budget 8 tool calls ถ้าครบให้หยุดโดยไม่สรุปว่าได้คำตอบครบ

## 5. ตรวจคำตอบอีกชั้น

แยกการเลือก tool ออกจากการขอ final JSON เพราะ prompt ให้ตอบ JSON ตลอดอาจรบกวน native tool calling ตรวจ JSON ด้วย Pydantic และตรวจว่า source IDs อยู่ในผลที่ค้นจริง อย่างไรก็ตามการมี citation ที่ถูก ID ยังไม่รับประกันว่าเนื้อหาทุกประโยคถูกต้อง

## 6. วัดก่อนเลือกวิธี

สร้างชุด 30 คำถามติด relevant IDs เทียบ vector top-1, vector top-3, BM25 top-3 และ hybrid top-3 ผล recall คือ .8000, .9833, .9667 และ .9833 ตามลำดับ ดังนั้นเลือก vector top-3 ความดีขึ้นจาก top-1 ส่วนหนึ่งคือมีงบให้หลาย chunk ต้องไม่พูดว่าเป็นความดีขึ้นของ hybrid โดยเฉพาะเมื่อเทียบที่ k=3 แล้วเสมอ

## 7. ทำให้เห็นข้อผิดพลาด

หน้า evaluation แสดง t27 ที่ถามทั้งเงินประกันกล้องและการอบรม แต่ค้นเงินประกันประเภทอื่นมาปน อีกกรณีคือ “ยืมได้กี่วัน” สั้นเกินไปสำหรับ lexical retriever ตอนนี้ ตัวเลข benchmark สูงเพราะคำถามถูกสร้างคู่กับ corpus จึงควรให้คนอีกคนเขียนคำถามใหม่และตรวจ labels

## 8. แยกสิ่งที่ทำแล้วกับสิ่งที่รอ

รันแอป, retrieval, SQL และ protocol tests แล้ว และทดสอบ class proxy จริงด้วย gemma-4-E4B-it สำเร็จ 3 สถานการณ์เมื่อ 25 ตุลาคม 2569 ผลอยู่ใน results/live-smoke.json สิ่งที่ยังต้องตรวจเพิ่มคือคำตอบรายข้อโดยคนและคำถามจากผู้ใช้อิสระ โหมด demo ยังคงเป็นกฎในโค้ดและไม่ถูกนำไปอ้างเป็นผลของ LLM

## ไฟล์ที่ควรเปิดอ่านก่อนอธิบาย

- `app/agent.py`: loop, stop condition, dispatcher และ JSON renderer
- `app/retrieval.py`: lexical vectors, BM25 และ RRF
- `app/inventory.py`: bound parameters และ query-only DB
- `scripts/evaluate.py`: สูตรและการเฉลี่ย metrics
- `results/retrieval.json`: ตัวเลขจริงและอันดับแต่ละคำถาม

## คำถามที่อาจารย์อาจถาม

- ทำไมไม่ใช้ hybrid? เพราะที่งบเท่ากันไม่ได้ดีกว่า vector top-3 ในชุดนี้
- ทำไม MRR=1 แต่ยังผิด? เพราะ metric สนใจ relevant ตัวแรก ไม่ได้เช็กว่าครบสองแหล่ง
- TF-IDF เป็น semantic embedding ไหม? ไม่ใช่ เป็น sparse lexical representation จึงพลาดคำที่ใช้คำต่างกันมากได้
- อะไรพิสูจน์ความปลอดภัย SQL? SQL มาจาก template, values bind เป็น parameters และ connection เป็น query-only; ไม่ใช่เชื่อ prompt อย่างเดียว
- Citation ตรวจอะไรได้? ตรวจว่ามีแหล่งนั้นจริงในผล tool แต่ต้องใช้คนตรวจว่าประโยคอ้างได้ตรงหลักฐานหรือไม่

## 9. ส่งเว็บแทนคลิปได้หรือไม่

โจทย์ให้เลือกคลิป 3-6 นาทีหรือ deployed working app URL อย่างใดอย่างหนึ่งได้ แต่ยังต้องอธิบายกรณีสำเร็จและ failure ในการ demo กับผู้สอน ไฟล์ deploy อยู่ใน render.yaml อ่านขั้นตอนได้ใน docs/deploy-th.md ต้องยืนยัน URL จริงก่อนใส่ README ไม่ใช้ localhost เป็น live link
